# Key Lifecycle (BSZ AIS-B2)

This document describes generation, usage, storage, and destruction of every key type used in gr-linux-crypto, for key lifecycle management and BSZ evaluation.

## Overview

All session keys and private key material must be securely zeroized when no longer needed. The module uses:

- **C++:** `OPENSSL_cleanse()` (when OpenSSL is available) or a compiler-barrier-protected overwrite via the `SecureBuffer` RAII class and `secure_clear()` helper.
- **Python:** `secure_zero(bytearray)` in `crypto_helpers` (uses `OPENSSL_cleanse` via ctypes when available).

## Key Types by Block

### 1. Kernel Keyring Source (`kernel_keyring_source`)

| Phase       | Description |
|------------|-------------|
| **Generation** | Keys are not generated by this block; they are read from the Linux kernel keyring via `keyctl(KEYCTL_READ)`. |
| **Usage**      | Key bytes are copied to the output stream; internal offset is updated. |
| **Storage**    | Key material is held in `d_key_data` (in-memory) only while the block is operating. |
| **Destruction**| On clear/reload and in the destructor, `secure_clear(d_key_data)` is used so key material is zeroized before the buffer is cleared. |

### 2. Kernel Crypto AES (`kernel_crypto_aes`)

| Phase       | Description |
|------------|-------------|
| **Generation** | Keys are not generated by this block; they are supplied via the key port (e.g. from kernel keyring or another source). |
| **Usage**      | Key bytes are passed to the kernel AF_ALG interface for encryption/decryption. |
| **Storage**    | No long-term in-process storage of key material in this block. |
| **Destruction**| Output buffers are zeroed with `memset` for unused regions; key material is not retained after the operation. |

### 3. Nitrokey Interface (`nitrokey_interface`)

| Phase       | Description |
|------------|-------------|
| **Generation** | Keys may be generated on the device or loaded from the host; the block does not generate keys itself. |
| **Usage**      | Key material is read from the Nitrokey into `d_key_data` and output to the stream. |
| **Storage**    | Held temporarily in `d_key_data` for the duration of the read. |
| **Destruction**| Before clearing or when done, key material in `d_key_data` is zeroized with `secure_clear(d_key_data)` (or equivalent); buffers are not released without prior zeroization. |

### 4. Brainpool ECIES Encrypt (`brainpool_ecies_encrypt`)

| Phase       | Description |
|------------|-------------|
| **Generation** | Ephemeral key pair and session key are generated per encryption; session key is derived via ECDH + HKDF. |
| **Usage**      | Session key and IV are used for AES-GCM encryption; only ciphertext and ephemeral public key are emitted. |
| **Storage**    | Session key and derived IV are local variables; not retained after the encrypt call. |
| **Destruction**| Local key/IV buffers are stack-allocated and go out of scope; any heap-backed key material is cleared with `secure_clear` before release. |

### 5. Brainpool ECIES Decrypt (`brainpool_ecies_decrypt`)

| Phase       | Description |
|------------|-------------|
| **Generation** | Shared secret is derived via ECDH from recipient private key and ephemeral public key; session key and IV from HKDF. |
| **Usage**      | Session key and IV are used for AES-GCM decryption; plaintext is written to output. |
| **Storage**    | `shared_secret` is a local vector; key/IV are local. |
| **Destruction**| `secure_clear(shared_secret)` is called after HKDF and before any continue/exit; key/IV are not retained. |

### 6. Brainpool ECIES Multi-Encrypt / Multi-Decrypt

| Phase       | Description |
|------------|-------------|
| **Generation** | Per-recipient ECDH shared secrets and optional Shamir-backed session key; session key derived via HKDF or Shamir reconstruct. |
| **Usage**      | Session key used for symmetric encryption/decryption; per-recipient ciphertext for encapsulated keys or shares. |
| **Storage**    | Shared secrets and session key held in local or member buffers only for the duration of the operation. |
| **Destruction**| All shared-secret and session-key buffers are cleared with `secure_clear` (or equivalent) before scope exit or reuse. |

### 7. Brainpool ECDSA Sign / Verify

| Phase       | Description |
|------------|-------------|
| **Generation** | Sign uses the provided private key; no session key is stored. |
| **Usage**      | Private key is used only for signing; verify uses only public key. |
| **Storage**    | Private key is supplied by the caller (e.g. key_input port); not stored inside the block beyond the operation. |
| **Destruction**| No long-lived key storage in the block; any temporary buffers are cleared when no longer needed. |

### 8. OpenPGP Card Helper (ECDH / key operations)

| Phase       | Description |
|------------|-------------|
| **Generation** | Shared secret is computed on the card or via supplied key. |
| **Usage**      | Shared secret is returned to the caller for HKDF/encryption. |
| **Storage**    | Returned in a vector; caller is responsible for zeroization. |
| **Destruction**| Callers (e.g. ECIES decrypt) use `secure_clear(shared_secret)` when done. |

## SecureBuffer and secure_clear (C++)

- **SecureBuffer:** RAII buffer that zeroizes its memory in the destructor using `OPENSSL_cleanse()` or a volatile write loop. Use for any heap-allocated key or secret that outlives a single function.
- **secure_clear(vector):** Zeroizes the vector’s contents and then clears it. Use for `std::vector<uint8_t>` or `std::vector<unsigned char>` that hold key material before releasing or reusing.

## secure_zero (Python)

- **secure_zero(buf: bytearray):** Zeroizes the mutable buffer in place using `OPENSSL_cleanse` via ctypes when available. Use for any bytearray that held key material before discarding or reusing. Immutable `bytes` cannot be zeroed in place; use a bytearray copy if zeroization is required.

## Testing

- **SecureBuffer:** Unit tests verify that a buffer zeroized on destruction does not contain the original bytes (e.g. via a custom allocator or memory inspection).
- **secure_zero:** Unit tests verify that after `secure_zero(ba)`, the bytearray contains only zeros.
- **No key material on heap:** CI can use Valgrind massif or AddressSanitizer to ensure no key material remains in heap after decrypt (or other key-using) operations.
